# AGENTS.md 精簡維護

Root 指令文件是每次請求都會被載入的 instruction budget——root 只留與每一個任務都相關的內容，其餘依主題拆分為由 root 連結、按需載入的分類文件，並在過程中消除矛盾、修剪冗餘。精簡是**搬遷與刪冗，不是改寫規則語意**。

> 判準背後的原理（instruction budget、context 毒化、monorepo 巢狀結構、來源引用）見 [`references/principles.md`](references/principles.md)——對判準有疑義、或使用者追問「為什麼要這樣拆」時再讀取。

## 兩個貫穿全程的測試

- **root 測試**：這條指令是否與 repo 中每一個任務都相關？——決定留在 root 或拆出（Step 3）。
- **行為測試**：這條指令會不會改變 agent 的具體行為？——決定保留或標記刪除（Step 5）。不會改變行為的指令只是純粹的 token 成本。

## 目標檔案

先讀取專案根目錄的 `AGENTS.md` 與 `CLAUDE.md`（兩者是同一慣例的等價實作），依實際狀態選擇處理路徑：

| 狀態 | 處理 |
|------|------|
| 只有一份存在（不論是哪份） | 以該檔為目標，直接進入流程。若只有 `CLAUDE.md`，可在 Step 6 提案中附帶**可選**建議：主內容遷至 `AGENTS.md`、`CLAUDE.md` 只留 `@AGENTS.md` 指標，以同時支援其他遵循 AGENTS.md 慣例的工具——是否採納由使用者決定 |
| 兩者都存在，其中一份只是**指標**（內容僅為 `@AGENTS.md` 之類的單行引用） | 以被指向的檔案為唯一目標；指標檔保持原樣，不納入盤點、不重複處理。重構落地後確認指標仍指向有效檔案 |
| 兩者都存在且**內容各自獨立**（不相符） | 視為**內容漂移（drift）**——同一份事實維護了兩份副本的必然結果。兩份一起盤點並統一編號；Step 2 的矛盾比對必須**跨檔**進行（同一件事兩檔說法不同即為矛盾組）。Step 6 提案合併為單一事實來源：主內容放 `AGENTS.md`、`CLAUDE.md` 改為 `@AGENTS.md` 指標（合併方向與衝突取捨以 AskUserQuestion 交使用者裁決） |

- **額外文件**：使用者可指定其他指令文件（如 `.cursorrules`、`.github/copilot-instructions.md`、既有的規範文件）一併納入盤點；跨檔矛盾比對同樣適用。

## 執行流程

### Step 1 — 盤點（Inventory）

讀取所有目標檔案，把內容逐條抽出並編號（I1、I2、…）。一條「指令」是一個會改變 agent 行為的可執行要求；純敘述性背景（專案描述等）也編號並註記為敘述。同時對照實際 repo 驗證指令中提到的檔案路徑與命令是否仍存在，失效者註記為**過時（stale）**。

**完成判準**：所有目標檔案讀畢，每一條指令都有編號；此後每個步驟以編號追蹤，直到流程結束時每個編號都有明確去向（root／某分類檔／刪除）為止，無一遺漏。

### Step 2 — 找出矛盾（Contradictions）

比對整份編號清單，列出所有互相衝突的指令組（例如某處說 `npm run test`、另一處說 `vitest run`）。對**每一組**矛盾，以 AskUserQuestion 詢問使用者裁決，選項至少含：保留版本 A、保留版本 B、合併改寫、兩者皆刪。

矛盾必須在檔案結構被拆散**之前**解決：一旦兩條互斥指令被分別歸進不同分類檔，矛盾就不再相鄰可見，日後更難發現；且「保留哪一條」是專案所有者的價值判斷，由使用者裁決而非代為決定。

**完成判準**：每一組矛盾都有使用者的明確裁決，清單中不再存在互斥指令。

### Step 3 — 萃取 root 本質（Essentials）

對每條指令套用 **root 測試**。通過者留在 root，其餘全部移出。

Root 的預期最小集：

- 一句話專案描述（實際扮演 role-based prompt 的角色）
- Package manager（非 npm 時才需要寫）
- 非標準的 build／typecheck 命令（標準做法不必寫）
- 極少數真正通過 root 測試的其他指令

**完成判準**：每條指令都標記為「root」或「非 root」，且每個 root 標記都能以 root 測試說明理由。

### Step 4 — 分組（Grouping）

把非 root 指令依主題聚類（以實際內容決定，常見如：TypeScript 慣例、testing patterns、API 設計、Git workflow）。每一組對應一個獨立 markdown 檔案。

**完成判準**：每條非 root 指令歸入且僅歸入一組；每組的主題名稱能讓 agent 從 root 的連結文字判斷「什麼任務需要讀它」。

### Step 5 — 標記刪除（Flag for deletion）

逐條檢查各分組內容，套用**行為測試**。未通過者依判準標記並採取**該判準專屬的修法**——只標記與提案，最終處置由使用者在 Step 6 裁決：

| 判準 | 定義 | 修法 |
|------|------|------|
| **Redundant（多餘）** | agent 預設就會做，或環境可直接查到（如標準 npm scripts、`package.json` 已載明的資訊） | 標記刪除 |
| **Too vague（太模糊）** | 無法轉化為具體行為 | **優先改寫為具體可執行的指令**；確實無法具體化才標記刪除 |
| **Overly obvious（過度顯而易見）** | 如「write clean code」 | 標記刪除 |
| **Stale（過時）** | Step 1 註記的失效路徑或命令 | 可對照 repo 找到現況者**改為更新**（如路徑搬家→改指新路徑）；已無對應物才標記刪除 |

#### 什麼不該標記刪除

以下內容即使乍看多餘或瑣碎，也必須保留——無輔助的清查會雙向失敗：刪掉有價值的規則、留下真正的空話。

- **專案特有的反直覺決策**：偏離常見預設的明確選擇（如「驗證錯誤回 422 不回 400」、「不使用 PUT」、「mutating endpoint 必附 idempotency key」）——這正是指令文件存在的理由。
- **非 npm 的 package manager 標註、非標準 build／typecheck 命令**：屬 root 最小集，不因「簡短」而誤判為多餘。
- **帶理由的例外說明**：解釋為何不採用某常見做法、為何抑制某警告的文字——理由本身就是行為約束。
- **量測數據與具體界限**：附有出處或數字的效能界限、限制值。

**圍欄**：對任何一條拿不準的指令，保留並在提案中註記「待裁決」，交由使用者決定——語意的改寫與刪除永遠不因「順手」而發生。

**完成判準**：每一組分類檔的每條指令都套用過行為測試，待刪與待改寫清單每項都附有對應判準與理由。

### Step 6 — 產出提案並落地（Structure & apply）

先完整輸出提案供使用者審閱：

1. 新的 root 全文（精簡內容 + 指向各分類檔的 markdown 連結，連結文字說明何時該讀）
2. 各分類檔案的路徑與完整內容
3. 建議的 `docs/` 資料夾結構（依專案既有慣例調整位置）
4. 待刪清單、待改寫清單與「待裁決」註記（各附判準與理由）

經使用者確認後才覆寫原檔並建立新檔；確認前原檔保持原樣。

**完成判準**：使用者確認後新結構已全部寫入，且 Step 1 的每個編號指令去向可回溯——落在新 root、落在某分類檔、或經使用者確認刪除／改寫。
