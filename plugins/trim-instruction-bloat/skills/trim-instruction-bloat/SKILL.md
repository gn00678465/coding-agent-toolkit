# AGENTS.md 精簡維護

Root 指令文件每次請求都會載入，是固定的 instruction budget。本 skill 把 root 精簡到只剩通過 **root 測試**的內容，其餘依主題拆成由 root 連結、按需載入的分類檔，過程中裁決矛盾、修剪冗餘。精簡是**搬遷與刪冗，不是改寫規則語意**。

> 判準背後的原理（instruction budget、context 毒化、monorepo 巢狀結構、來源引用）見 [`references/principles.md`](references/principles.md)——對判準有疑義、或使用者追問「為什麼要這樣拆」時再讀取。

## 貫穿全程的規則

- **root 測試**：這條指令是否與 repo 中每一個任務都相關？→ 決定留 root 或拆出（Step 3）。
- **行為測試**：這條指令會不會改變 agent 的具體行為？→ 決定保留或標記（Step 5）。不改變行為的指令只是 token 成本。
- **編號追蹤**：Step 1 給每條指令的編號是全程的追蹤鍵，直到 Step 6 每個編號都有可回溯的去向。
- **只標記、不裁決**：語意的刪除、改寫、新增（含檔案合併方向）在流程中一律**標記**並附判準，於 Step 6 提案交使用者裁決；拿不準的條目標記「待裁決」。矛盾是唯一例外——在 Step 2 當場以 AskUserQuestion 裁決。

## 目標檔案

讀取專案根目錄的 `AGENTS.md` 與 `CLAUDE.md`（同一慣例的等價實作），依狀態決定目標：

| 狀態 | 處理 |
|------|------|
| 只有一份 | 以該檔為目標。若只有 `CLAUDE.md`，Step 6 提案可附帶**可選**建議：主內容遷至 `AGENTS.md`、`CLAUDE.md` 只留 `@AGENTS.md` 指標，以支援其他遵循 AGENTS.md 慣例的工具 |
| 兩份並存，其中一份是**指標檔**（內容僅為 `@AGENTS.md` 之類的單行引用） | 以被指向的檔案為唯一目標；指標檔不納入盤點，落地後確認指標仍指向有效檔案 |
| 兩份並存且**內容各自獨立** | 視為**漂移（drift）**：同一份事實維護了兩份副本。兩份同列目標；同一件事兩檔說法不同即為 Step 2 的矛盾組。Step 6 提案合併為單一事實來源：主內容放 `AGENTS.md`、`CLAUDE.md` 改為 `@AGENTS.md` 指標 |

使用者指定的其他指令文件（其他 agent 平台的 rules 檔、既有規範文件等）同列為目標檔案。

## 執行流程

### Step 1 — 盤點（Inventory）

讀取所有目標檔案，逐條抽出並編號（I1、I2、…）。一條「指令」是一個會改變 agent 行為的可執行要求；純敘述性背景（專案描述等）也編號並註記為敘述。對照實際 repo 驗證指令中的檔案路徑與命令，失效者註記為 **stale**。

引用的外部工具、skill、agent 名稱屬環境相依引用：能在當前環境驗證者依 stale 規則處理（存在→保留、更名→標記更新、消失→列為矛盾組）；無法驗證者保留原文並註記「未驗證」。

**升級候選**：若 repo 中存在指令文件以外的持久記錄（版本控管的工作日誌、交接文件、貢獻指南、CI／hook 設定），掃描其中標註為長期有效且反覆被引用的行為規則，另以 U1、U2…編號。升級候選是**新增語意**（非搬遷），在 Step 6 獨立成段逐條裁決。

**完成判準**：所有目標檔案讀畢，每一條指令都有編號。

### Step 2 — 找出矛盾（Contradictions）

跨所有目標檔案比對整份編號清單，列出互相衝突的指令組（例如兩處對同一測試命令給出不同指示）。除「指令 vs 指令」外，須含「**指令 vs repo 可觀測實務**」：以實際目錄結構、測試佈局、版本控管內的執行證據，驗證指令是否與現行實務相符，不符者同列矛盾組。對**每一組**矛盾以 AskUserQuestion 詢問使用者，選項至少含：保留 A、保留 B、合併改寫、兩者皆刪。

矛盾必須在結構拆散**之前**解決：互斥指令一旦分進不同分類檔就不再相鄰可見；且保留哪一條是專案所有者的價值判斷。

**完成判準**：每一組矛盾都有使用者的明確裁決，清單中不再存在互斥指令。

### Step 3 — 萃取 root 本質（Essentials）

對每條指令套用 **root 測試**。通過者留在 root，其餘全部移出。

Root 的預期最小集：

- 一句話專案描述（實際扮演 role-based prompt）
- Package manager（非 npm 時才寫）
- 非標準的 build／typecheck 命令
- 極少數真正通過 root 測試的其他指令

**完成判準**：每條指令都標記為「root」或「非 root」，每個 root 標記都能以 root 測試說明理由。

### Step 4 — 分組（Grouping）

把非 root 指令依主題聚類（以實際內容決定，常見如 TypeScript 慣例、testing patterns、API 設計、Git workflow）。每組對應一個獨立 markdown 檔。

**完成判準**：每條非 root 指令歸入且僅歸入一組；每組主題名稱能讓 agent 從 root 的連結文字判斷「什麼任務需要讀它」。

### Step 5 — 標記刪除（Flag for deletion）

逐條對各分組內容套用**行為測試**，未通過者依判準標記並採該判準專屬的修法：

| 判準 | 定義 | 修法 |
|------|------|------|
| **Redundant** | agent 預設就會做，或環境可直接查到（標準 npm scripts、`package.json` 已載明的資訊） | 標記刪除 |
| **Too vague** | 無法轉化為具體行為 | **優先改寫為具體可執行的指令**；確實無法具體化才標記刪除 |
| **Overly obvious** | 如「write clean code」 | 標記刪除 |
| **Stale** | Step 1 註記的失效路徑或命令 | 可對照 repo 找到現況者**標記更新**（路徑搬家→改指新路徑）；已無對應物才標記刪除 |

#### 必須保留

以下內容即使乍看瑣碎也保留——無輔助的清查會雙向失敗：刪掉有價值的規則、留下真正的空話。

- **專案特有的反直覺決策**：偏離常見預設的明確選擇（「驗證錯誤回 422 不回 400」、「不使用 PUT」、「mutating endpoint 必附 idempotency key」）——這正是指令文件存在的理由。
- **Step 3 root 最小集的項目**：不因簡短而誤判為 redundant。
- **帶理由的例外說明**：為何不採用某常見做法、為何抑制某警告——理由本身就是行為約束。
- **量測數據與具體界限**：附有出處或數字的效能界限、限制值。

**完成判準**：每一組分類檔的每條指令都套用過行為測試；待刪與待改寫清單每項附判準與理由。

### Step 6 — 產出提案並落地（Structure & apply）

先完整輸出提案供審閱：

1. 新 root 全文（精簡內容 + 指向各分類檔的 markdown 連結，連結文字說明何時該讀）
2. 各分類檔的路徑與完整內容
3. 建議的 `docs/` 資料夾結構（依專案既有慣例調整位置）
4. 待刪、待改寫、待裁決清單（各附判準與理由）
5. 升級候選清單獨立成段（U 編號，逐條附來源出處），僅使用者核可者寫入

經使用者確認後才覆寫原檔並建立新檔。

落地後對每個被移除或搬遷的段落名、識別字、工具引用，做全 repo、**不限副檔名**（含設定檔與腳本）的反向 grep 至零殘留。只增不改的歷史稽核文件（決策記錄、封存日誌）可排除，排除清單須在提案中列明。

**完成判準**：新結構已全部寫入；Step 1 每個編號的去向可回溯——新 root、某分類檔、或經使用者確認的刪除／改寫；反向 grep 零殘留（或殘留僅在已列明的排除清單內）。
