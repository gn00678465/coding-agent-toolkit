# Superagent Brief 與裁定模板

> [!IMPORTANT]
> 給所有 Worker 的檔案路徑（尤其派給 `agy` 時）**一律使用絕對路徑**，避免子代理在獨立 worktree 或沙盒內組錯相對路徑而觸發權限對話框。

---

## 1. 實作 Brief（`brief.md`）

```markdown
# 階段 <NN>-<slug>：實作 Brief

## Mandate（目標與邊界）
- **目標**：<一句話說明本批要達成的行為或修正>
- **起點（base）**：`<commit SHA 或 branch>`
- **工作目錄（worktree）**：`<worktree 絕對路徑>`（分支 `<branch-name>`）
- **允許修改範圍**：<明確列出負責的檔案／模組>
- **禁止碰觸範圍**：<不可修改的目錄、設定檔、外部真實服務、機密>

## 不變量與邊界條件
| 情境 / 邊界 | 預期行為 | 不可違反的不變量 |
|---|---|---|
| <邊界 1> | <結果> | <不變量> |
| <邊界 2> | <結果> | <不變量> |

## 必要驗證與日誌規定
所有測試與檢查輸出必須寫入 `<logs 絕對路徑>\`，且每份 `.log` 最後一行必須寫 `exit=<結束碼>`：
1. 格式／靜態檢查：`<指令>` → `<logs>\lint.log`
2. 單元與整合測試：`<指令>` → `<logs>\test.log`
3. 變異驗證（適用修正或關鍵邊界）：暫時還原修法確認新測試失敗 → `<logs>\mutation.log`，再還原回修法重跑通過。

## 報告格式與完成標記
- 報告寫至：`<report 絕對路徑>`
- 必須包含：修改摘要（含 `檔案:行號`）、驗證結果與每份 log 路徑及 `exit=`、提交的 `commit SHA`、任何未處理的邊界或已知限制。
- **所有檢查通過並完成 commit 後**，才在報告最後一行單獨寫上完成標記：

IMPL DONE
```

## 2. 修正 Brief（`brief_r<n>.md`，`n` ≤ 3）

```markdown
# 階段 <NN>-<slug>：第 <n> 輪修正 Brief

- **工作目錄（worktree）**：`<worktree 絕對路徑>`（接續既有分支 `<branch-name>`）
- **裁定依據**：`<ruling_r<n>.md 絕對路徑>`

## 本輪採納需修正項目（僅修下列項目，勿擴張範圍）
1. **[P1/P2] <問題標題>**
   - 位置：`<絕對路徑:行號>`
   - 根因與要求：<具體要求與預期不變量>
   - 必補測試與變異驗證：<測試名稱與變異日誌路徑>

## 驗證與回報
- 跑完完整驗證寫入 `<logs 絕對路徑>\r<n>_*.log`（結尾 `exit=<code>`）。
- 修正報告寫至：`<report_r<n>.md 絕對路徑>`
- 完成後於最後一行單獨寫上：

FIX R<n> DONE
```

## 3. 獨立審查 Brief（`review_brief_<id>.md`）

適用於 `codex`（預設看正確性／並行／測試品質）與 `agy`（預設看設計一致／安全／EGM 視角）。

```markdown
# 階段 <NN>-<slug>：獨立審查 Brief（<審查者角色：A 正確性 / B 安全與設計>）

## 審查範圍與輸入（一律絕對路徑）
- **專案目錄**：`<repo 或 worktree 絕對路徑>`
- **比對範圍**：`git diff <base>..<head>`（若含多輪修正請看整批累積 diff）
- **任務契約**：`<brief.md 絕對路徑>`
- **實作報告**：`<report.md 絕對路徑>`
- **設計規格**：`<design doc 絕對路徑，若有>`

## 審查原則
1. **獨立核對，不輕信報告**：直接讀取程式碼確認實作與報告宣稱是否一致。
2. **只列真實問題，標明嚴重度**：
   - **P1（阻斷）**：資料損毀／遺失、安全漏洞、死鎖、規格明文違反、核心功能錯誤。
   - **P2（應修）**：邊界條件錯誤、測試未覆蓋關鍵路徑、錯誤處理缺失導致靜默失敗。
   - **P3（建議／既有問題）**：風格改善、罕見極端情境、本批前已存在的問題（單獨分節，不列入 FAIL）。
3. **誠實標註驗證限制**：若本輪為靜態審查未實跑測試，須在報告註明「未實跑，屬靜態推導」。
4. 若工具系統提示建議使用外部索引工具（如 codebase-memory-mcp），本審查以直接讀取上述絕對路徑與 `git diff` 為準。

## 輸出與完成標記
- 報告寫至：`<review_report_<id>.md 絕對路徑>`
- 最後一行必須單獨寫上判定（只能二選一）：
  - 無成立的 P1 / P2：`VERDICT: PASS`
  - 有任一成立的 P1 / P2：`VERDICT: FAIL`
```

## 4. Router 裁定紀錄（`ruling_r<n>.md`）

```markdown
# Router 裁定：階段 <NN>-<slug> 第 <n> 輪審查（YYYY-MM-DD）

- **審查來源**：`<review_report_a.md>`（<PASS/FAIL>）、`<review_report_b.md>`（<PASS/FAIL>）
- **Router 核對紀錄**：<核對過哪些程式位置、是否補跑了審查者未實跑的檢查>

| # | 來源 | 嚴重度 | 問題摘要 | 裁定（採納 / 降級 P3 / 駁回 / 記已知限制） | 理由與證據 |
|---|---|---|---|---|---|
| 1 | A | P2 | <摘要> | 採納 | <核對 `file:line` 確認成立> |

## 下一步決議
- [ ] 進入第 `<n+1>` 輪修正（`brief_r<n+1>.md`）
- [ ] 達 3 輪上限 → 停止修補，整合 3 輪報告修訂 `brief.md`，丟棄分支從 base 重做
- [ ] 全部通過 → 執行 `verify-gate`、合併、驗證與收尾
```
